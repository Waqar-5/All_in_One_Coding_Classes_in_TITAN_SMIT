01
Why and where we use APIs
The invisible glue of every modern app
Definition
An API is the messenger between two software systems
API stands for Application Programming Interface. It defines a set of rules for how two pieces of software talk to each other. One side requests, the other responds. You don't need to know what's happening inside — you just use the interface.
 Think of a waiter at a restaurant. You tell the waiter what you want (client). The waiter goes to the kitchen (server) and returns with your food. You never enter the kitchen yourself — the waiter is the API.
Where APIs are used every day
Google Maps in Careem/Uber Stripe payment at checkout Weather on your phone Sign in with Google WhatsApp Business messages Instagram feed loading
Why we need APIs
APIs let us reuse instead of rebuild — no need to build a payment system, maps, or login from scratch. They also act as security gatekeepers, keeping your database hidden from the outside world. Multiple apps (web, mobile, desktop) can all use the same API without duplicating logic.
02
REST API vs GraphQL
Two philosophies, one goal
REST API
Fixed menu, server decides
Many endpoints — one per resource. The server gives you a predefined shape of data whether you need it all or not.
Simple and widely understood
Easy browser caching (GET requests)
Familiar to every developer
Over-fetching — too much data
Under-fetching — multiple round trips
GraphQL
Build your plate, client decides
One single endpoint. You request exactly the fields you need — nothing more, nothing less.
No over or under fetching
One request for all related data
Self-documenting schema
Harder to cache
Steeper learning curve
The core problem REST has
Over-fetching and Under-fetching
Over-fetching: You call /users/42 and get 20 fields back, but you only needed the name. Wasted bandwidth.

Under-fetching: You need a user's name + posts + followers. With REST that's 3 separate requests. With GraphQL it's 1.
Where each is used in real life
REST — Weather, News, Currency APIs REST — Microservices GraphQL — GitHub API v4 GraphQL — Shopify Storefront GraphQL — Mobile apps (save data)
03
JSON vs XML — why JSON won
The universal data language of the web
Why we need a data format
Servers can't send JavaScript objects over a wire
Data in memory (variables, objects, arrays) can't travel across a network. It must be converted to plain text first, sent, then converted back. JSON and XML are both text formats that do this job. This process is called serialization (object → text) and deserialization (text → object).
JSON
Lightweight and readable
Looks like a JavaScript object. Key-value pairs. Clean, minimal, easy to scan at a glance. Every modern language reads it natively.
XML
Verbose and tag-heavy
Uses opening and closing tags like HTML. Every field is wrapped twice. Same data takes 2–3× more text to express. Harder to read for humans.
The analogy that makes it click
XML is like sending a formal letter: "Dear Recipient, the temperature is: 32 degrees, Yours sincerely." JSON is like a text message: "temp: 32". Same information — far less noise.
Where XML is still alive
RSS feeds (news & podcasts) SOAP — banking & enterprise APIs Microsoft Office files (.docx, .xlsx)
04
All HTTP Methods
How you tell the server what action to take
HTTP methods (also called verbs) are the actions you perform on a resource. Together they map to CRUD — Create, Read, Update, Delete. Every API request uses exactly one method.
GET Read — fetch data from the server
Retrieves a resource without modifying it. Safe to repeat as many times as you want — it never changes anything on the server. It is read-only.
Opening Instagram — your app sends GET requests to fetch your feed, stories, and DMs.
POST Create — send new data to the server
Submits data to create a new resource. Data travels in the request body, not the URL. Each request creates something new.
Signing up for an account — you fill the form and click submit. A POST request sends your name, email, and password to create your account.
PUT Replace — overwrite the entire resource
Replaces the complete resource with a new version. You must send all fields — even ones you didn't change. Missing fields get erased.
Editing your full LinkedIn profile — you resubmit name, bio, location, and job title all at once. The server replaces everything it had before.
PATCH Update — change only specific fields
Partially updates a resource. You send only what changed — the server merges it in. Fields you don't mention stay untouched.
Changing only your WhatsApp profile picture — you don't resend your name or status. Just the new photo. The server patches that one field.
DELETE Remove — permanently delete a resource
Deletes the specified resource from the server. Once done, it's gone.
Deleting a tweet, removing a product from your cart, or deactivating your account.
HEAD Check — headers only, no body
Like GET, but returns only headers — no actual content. Used to check if a resource exists or get its size/date without downloading it.
A download manager checking file size before starting the download — using HEAD, not GET.
PUT vs PATCH — the definitive difference
PUT = Rewrite the whole page. If you forget to include something, it's gone.
PATCH = Cross out one line and write the update. Everything else stays.

Rule of thumb: If you're sending a complete object → PUT. If you're updating one field → PATCH.
05
HTTP Status Codes — full list
The server's reply in a number
Every API response includes a 3-digit code. The first digit tells you the category instantly. 2xx = success, 3xx = redirect, 4xx = your fault, 5xx = server's fault.
2xx Success
200
OK
Request worked perfectly. Standard success for GET, PUT, PATCH responses.
201
Created
A new resource was successfully created — returned after a POST. Example: user registered successfully.
204
No Content
Success but nothing to return. Common after DELETE — the item is gone, nothing to send back.
3xx Redirect
301
Moved Permanently
Resource has a new permanent URL. Browsers and search engines update their links automatically.
302
Found (Temp Redirect)
Temporarily at a different URL. Used in login flows — "go here for now."
304
Not Modified
Resource hasn't changed since last fetch. Your cached version is still valid — saves bandwidth.
4xx Client Error — you did something wrong
400
Bad Request
Your request is malformed or missing required fields. Like submitting a form without filling required fields.
401
Unauthorized
You're not logged in or your token is missing/expired. "Who are you?" — trying to open Gmail without signing in.
403
Forbidden
You're logged in but don't have permission. "I know who you are, but you can't come in." — a user trying to access the admin panel.
404
Not Found
Resource doesn't exist at that URL. Wrong link, deleted item, or mistyped endpoint. The most famous status code.
405
Method Not Allowed
You used the wrong HTTP verb. The endpoint accepts GET only but you sent DELETE.
409
Conflict
Request conflicts with current state. Example: registering with an email that already exists in the system.
422
Unprocessable Entity
Data format is valid but the values make no sense. Example: age field contains a negative number — it parsed but is invalid.
429
Too Many Requests
Rate limit hit — you're sending too many requests too fast. APIs throttle you to protect their servers.
5xx Server Error — the server messed up
500
Internal Server Error
Something crashed on the server. Generic catch-all. Not your fault — it's a bug in the server code.
502
Bad Gateway
The middleman server got a bad response from the upstream server. Common in proxy and load balancer setups.
503
Service Unavailable
Server is down or overloaded. Usually temporary. Real life: an e-commerce site crashes during a big sale event.
504
Gateway Timeout
The middleman didn't get a response in time from the upstream server. Network congestion or overloaded backend.

Promise vs Promise.all
Handling things that take time
What is a Promise?
A placeholder for a value that doesn't exist yet
When you make an API call, the result isn't instant — it travels across a network. A Promise says "I don't have the answer right now, but I promise to give it to you when it's ready." Your code keeps running while it waits.
 You order food on Foodpanda. Your order is pending. When it arrives — fulfilled. If the restaurant cancels — rejected. You keep living your life while waiting — you don't stand at the door doing nothing.

Promise.all — parallel execution
Run multiple promises simultaneously
Promise.all takes an array of Promises and runs them all at the same time (in parallel). It waits for ALL of them to finish, then returns all results together. If even one fails, everything fails.
 Cooking dinner — you put rice on the stove, chicken in the oven, and salad in the fridge all at the same time. You don't wait for the rice before starting the chicken. When everything finishes together — you serve. That's Promise.all.
Other Promise helpers
allSettledGet all results — success or fail
Like Promise.all but doesn't stop if one fails. Returns results for all promises — fulfilled or rejected. Use when you want everything no matter what.
Loading a dashboard with weather, news, and stocks — even if weather fails, still show news and stocks.
raceFirst to finish wins
Returns as soon as the FIRST promise resolves or rejects. Perfect for timeouts — race your API call against a 5-second timer.
If your API doesn't respond within 5 seconds, show a timeout error. Race the API call against a timer.
anyFirst success wins
Returns when the first one SUCCEEDS. Only fails if ALL of them fail. Great for trying multiple servers and using the fastest one.
Try 3 backup servers — use whichever responds first. If all 3 fail, then show an error.
07
Try / Catch — Error Handling
Never let your app crash silently
What is Try/Catch?
Your app's safety net for anything that can go wrong
When you make an API call, a thousand things can fail — no internet, server down, expired token, wrong data format. Without error handling, your app shows a blank screen or crashes. Try/Catch is how you handle these failures gracefully and show the user something useful instead.
 Try block: You're driving normally. Catch block: If the car breaks down, you don't abandon it — you pull over and call for help. Finally block: No matter what happens, you always turn off the engine when done.
Real crash scenarios — with and without error handling
Scenario 1Network failure on a flight
Without catch: Blank white screen. User panics, thinks the app is broken.
With catch: You show "No internet connection. Please try again." with a retry button. User knows exactly what happened.
Scenario 2Login token expires
User leaves the app open for 2 hours. Token expires. They click something and the API returns 401.
Without catch: Nothing happens, app freezes.
With catch: You detect 401, clear the old token, redirect to login with "Your session expired. Please log in again."
Scenario 3Server crash during payment
User clicks "Pay Now." Payment server is overloaded — returns 503.
Without catch: Broken page. User doesn't know if they were charged. Panic, support tickets.
With catch: "Payment server is busy. Your card was NOT charged. Please try in a moment." — calm, informative.
Golden rule of error handling
Always show the user something meaningful when something goes wrong. Never show a blank screen. Never silently swallow the error. Tell them what happened and what they can do next. Errors are not failures — unhandled errors are.
When to use Try/Catch
Every API call JSON parsing User input processing Database operations File reading/writing
